## high: Blocking text reads can stall streaming and deadlock output draining

id: fnd_sig-feat-library-2d56c14338-2daa_af408aab54
category: concurrency
confidence: high
triage: confirmed-bug
status: open
feature: Python source src/slop_code/execution/:local (feat_library_2d56c14338)

evidence:
- src/slop_code/execution/local_streaming.py:130-142 (LocalStreamingRuntime._start_process)
- src/slop_code/execution/local_streaming.py:158-176 (LocalStreamingRuntime._create_demuxed_stream)

Selector readiness guarantees that some bytes can be read, but TextIOWrapper.read(8192) on a blocking pipe can continue waiting for 8192 characters or EOF. A child that flushes a short stdout message and remains running will not reliably deliver that message promptly. If it subsequently fills stderr, the reader remains blocked on stdout while the child blocks writing stderr, causing a deadlock. bufsize=0 does not make the text wrapper nonblocking.

recommendation:
Read available bytes from binary pipes using nonblocking reads or bounded raw reads, and decode each stream incrementally.

test analysis:
Existing output tests use short-lived commands and small mixed output. They assert final content rather than delivery before process exit or progress when the other pipe fills.

suggested regression test:
Extend mixed-output coverage with a synchronized child that emits a short flushed marker followed by stderr exceeding pipe capacity. Assert prompt marker delivery and complete draining under an independent watchdog, including split multibyte characters.

minimum fix scope:
Streaming subprocess pipe configuration, _create_demuxed_stream, and streaming output tests.

repro:
Run a child that flushes a short stdout marker, writes more than a pipe's capacity to stderr, and then exits. The demultiplexer can block waiting for additional stdout while stderr remains undrained.
