# Validate and analyze completed runs

1. Accept only a terminal experiment handoff payload from `experiment-lifecycle`. The payload MUST contain the objective, declared experimental variable and values, fixed controls, and, for every configured execution: experiment identifier; canonical terminal state; repository-relative paths to resolved configuration, provenance, run summary, checkpoint results, quality metrics, and telemetry required for claims; and checkpoint-keyed paths to per-checkpoint evaluations. Do not launch, monitor, resume, stop, or otherwise manage experiment lifecycle work.
2. Establish the completed cohort only from executions whose canonical terminal state and required artifact paths are complete, repository-relative, readable, and traceable. Preserve rejected execution identifiers, supplied paths, and rejection reasons. For comparisons, verify every fixed control is equivalent and the declared experimental variable has its expected value for each member. Exclude unmatched artifacts rather than normalizing them.
3. For every included run, verify that its resolved configuration, manifest/provenance, run summary, checkpoint results, per-checkpoint evaluations, quality metrics, and telemetry needed for a claim are present and mutually traceable through their repository-relative paths and experiment identifier. A manifest/provenance artifact may supply the inventory only when it enumerates and resolves every required artifact. Preserve all artifact-relative paths, experiment identifiers, checkpoint keys, and completed-cohort decisions.
4. For every included run, load scoring state through `load_verified_current_generation_state` before making a scoring-quality claim. Treat that API and `load_verified_current_generation` as the only scoring authority. Do not independently reconstruct manifest hashes, publication eligibility, symbol identities, test groups, transition completeness, or sidecar integrity. Treat `result.json` and `experiment_summary.txt` only as display projections.
5. Read canonical producer rows from the verified generation's `producer_status.json`. Use numeric benchmark values only when `load_verified_current_generation` accepts the generation. Use a component observation only when its owning canonical producer is successful; otherwise render the component as `Unavailable` and preserve its canonical `blocked_by` reason as a limitation. Never translate missing, blocked, gap, or invalid evidence to zero or one.
6. Compare or aggregate scoring quality only across runs with identical formula ID, evaluator identity, assessment policy, and configured problem set. Exclude unmatched scoring observations rather than normalizing them. Report evaluator identity only as implementation, cache tag, and executable SHA-256; never expose an absolute executable path.
7. Recalculate all reported totals, percentages, deltas, ratios, and rankings from persisted artifacts. Never infer missing measurements, substitute zero, or copy unsupported summary values.
8. Compute, for every included model, the mean pass rate across all checkpoints and the checkpoints with 100% pass rate. Treat a completed checkpoint count as execution coverage, not correctness. A checkpoint has 100% pass rate only when every required case under the equivalent assessment policy passed.
9. Identify measured failure evidence by model and checkpoint, but keep it as candidate evidence until Step 2 reconciles it with `fault-catalog`. Do not use a fault name in observations output before that reconciliation.
10. Prepare evidence-first analysis for the full report: observed outcomes, measured metrics, traceable artifact paths, verified scoring provenance, quality-component trajectories, and clearly separated interpretations. Record limitations caused by run count, seeds, checkpoints, pass policy, thinking level, unavailable metrics, blocked producers, or any excluded non-equivalent artifact.
